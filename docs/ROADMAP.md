# 迭代规划

本文规划内网防护系统从"能用的基础防守"到"满足攻防演练防守方要求、可长期运营"的演进路线。
每个版本都写明目标、范围和**验收标准**；版本完成后在此更新状态，并据试运行和实际使用的反馈调整后续顺序。

## 1. 定位与目标

**定位**：面向中大型企业内网的防守方平台，帮安全团队做到四件事：

| 能力 | 含义 | 衡量 |
| --- | --- | --- |
| 看得见 | 资产、主机行为、网络流量都在视野内 | 资产覆盖率（装了 Agent 的主机 / 全部主机）、日志源覆盖 |
| 判得准 | 真正的攻击能检出，正常行为不打扰 | 检出率（攻击模拟验证）、误报率（被标为误报的告警占比） |
| 处置快 | 发现后几分钟内能阻断 | MTTD（平均发现时间）、MTTR（平均处置时间） |
| 可运营 | 好装、好用、好扩展，几千台规模稳定 | 安装时长、单人可值守的主机数、万台压测指标 |

**明确不做**：

- 攻击工具（漏洞利用、横向移动、免杀等）。"攻"只体现为对**自己系统**的无害攻击模拟，用于验证检测能力。
- 通用 CVE 全量扫描、Web 漏洞扫描：对接专业扫描器，把结果导入漏洞库。
- 内核驱动级的主动拦截（Windows 驱动、Linux LSM 拦截）：开发和兼容成本远超收益，处置以用户态手段为主。
- 替代防火墙 / WAF / 堡垒机：与之联动，不重复建设。

## 2. 现状（v0.1）

已完成：资产发现、主机审计（SSH 登录 / sudo / 文件完整性 / 可疑进程）、Suricata 流量检测、漏洞与弱口令检测、
mTLS 节点认证、PostgreSQL / ClickHouse、告警推送、操作审计、一键安装。详见 [ARCHITECTURE.md](ARCHITECTURE.md)。

按攻击链对照 MITRE ATT&CK 的大致覆盖：

| 攻击阶段 | 覆盖 | 说明 |
| --- | --- | --- |
| 侦察 / 扫描 | ◑ | Suricata 扫描规则；无主机侧扫描检测 |
| 初始访问 | ◑ | 弱口令、未授权访问的事前发现；漏洞利用靠 Suricata 规则 |
| 执行 | ○ | 看不到命令行，只能识别临时目录程序 |
| 持久化 | ◑ | cron、authorized_keys、systemd、ld.so.preload 文件变更 |
| 提权 | ○ | sudo 审计有记录，无判断 |
| 凭据获取 | ◑ | SSH 爆破；无 Windows / 域 |
| 横向移动 | ○ | 无内网登录关系分析、无 Windows |
| 命令控制（C2） | ◑ | 仅 Suricata 规则；无外联行为分析、无威胁情报 |
| 防御规避 | ○ | Agent 可被直接停掉，只有离线告警 |

**最大的三个缺口**：Windows / 域控不可见；看不到进程命令行；只能告警不能处置。
**还有一个前提问题**：没有在真实攻击下验证过检出率，后续每加一项检测都应能被验证。

## 3. 原则

1. **检测即代码**：每条检测规则有唯一 ID、ATT&CK 技术编号、级别、说明、处置建议，**并配一个攻击模拟用例**；
   没有验证用例的规则不合入。
2. **误报优先于覆盖**：值守人员被误报淹没比漏掉一类攻击更危险。新规则先以"观察"模式上线，误报率达标后才推送告警。
3. **默认安全**：危险操作（弱口令检测、处置动作）默认关闭或需要审批，全部进审计日志。
4. **每个版本都可在真实环境跑通**：CI 中用真实 Linux 跑一键安装和攻击模拟，不再只依赖开发机上的模拟。
5. **小步发布**：开发按天推进，但每个版本发布后先在试运行环境跑起来再推广，不攒大版本。

## 4. 版本规划

开发由 AI 完成，**开发时间按天计**；真正决定进度的是**验证**：

- **CI 当天可验证**：GitHub Actions 提供有 root、systemd、较新内核的 Ubuntu 和 Windows 机器，
  一键安装、eBPF / auditd、攻击模拟、Windows Agent 的基础功能都能在 CI 中真实执行。
- **需要专门环境**：域控检测需要测试 AD 域；国产系统需要对应的机器。
- **只能按日历时间观察**：误报率要真实流量跑至少一周；检测效果最终要在真实攻防演练中检验。

规模：S = 几小时，M = 约半天，L = 约 1 天（均指开发 + CI 验证）。

**验收**：CI 全绿；试运行检查清单全部通过；记录到一周的告警量和误报样本。

**进展**：CI 已上线（SQLite / PostgreSQL / ClickHouse、govulncheck、npm audit、真实 Ubuntu 26.04 + systemd 端到端 18 项），

### v0.2 蜜罐与攻击模拟自检（✅ 已完成，诱饵凭据移到 v0.3）

**目标**：用最小代价拿到"几乎零误报"的入侵信号；建立检测验证框架，后续所有检测都在其上验证。

| 事项 | 规模 |
| --- | --- |
| 探针内置低交互蜜罐：SSH、RDP、SMB、MySQL、Redis、HTTP 管理后台等伪装端口，记录连接与登录尝试，任何访问即高危告警 | M |
| 蜜罐在资产页标识，不参与资产告警；支持一键部署到指定网段 IP | S |
| 蜜罐凭据（"诱饵账号"）：在主机上放置假的配置文件 / 历史命令，诱饵凭据被使用即告警 | S |
| 检测规则统一结构：规则 ID、ATT&CK 编号、级别、说明、处置建议；控制台可查看规则清单与覆盖矩阵 | S |
| 攻击模拟自检：控制台对选定主机下发无害模拟动作（模拟爆破、写测试 cron 文件、访问蜜罐、发送测试流量触发 IDS 规则），自动核对是否在预期时间内告警，生成"检测有效性报告" | M |

**验收**：内网任意主机访问蜜罐 10 秒内告警推送；自检覆盖现有全部检测规则且全部通过；自检纳入 CI。

**结果**：真实 Ubuntu 上蜜罐访问 4 秒内产生告警；三个自检场景全部检出（访问蜜罐 0.5 秒，文件篡改、临时目录执行
各约 30 秒即一个 Agent 采集周期），并纳入 CI。12 条检测规则中 3 条有自检覆盖，其余依赖日志或流量，
需要在 v0.3 起逐步补充自检场景（如模拟 SSH 爆破）。诱饵凭据需要在业务主机上放置文件，留到 v0.3 与主机检测一起设计。

### v0.3 主机检测深化（✅ 已完成，诱饵凭据另行设计）

**目标**：补上"看不到攻击者执行了什么"的缺口。

| 事项 | 规模 |
| --- | --- |
| 进程与命令行审计：内核 ≥ 4.18 用 eBPF（execve、connect），老内核（如 CentOS 7）回退 auditd | L |
| 检测规则：反弹 shell、`curl/wget \| sh` 下载执行、Web 服务进程派生 shell（Webshell 迹象）、临时目录执行、可疑提权（SUID、sudo 异常）、挖矿特征 | M |
| 内网登录关系：谁从哪台登录到哪台，识别异常横向（首次出现的登录路径、一台机器短时间登录多台） | M |
| Webshell 文件检测：Web 目录新增 / 修改脚本文件告警，结合可疑函数特征 | S |
| Agent 自保护：二进制与配置完整性自检、被停止 / 卸载 / 配置被改时上报；与离线告警区分"正常关机"和"被停止" | S |
| Agent 资源上限（CPU / 内存 cgroup 限制）与事件采样，保证不影响业务 | S |

**验收**：攻击模拟中反弹 shell、下载执行、Webshell 派生命令全部检出；Agent 在 4 核主机上 CPU 平均 < 2%；
三种发行版 + CentOS 7 均可用。

**结果**：命令审计改用内核进程连接器而非 eBPF（无需编译工具链，内核 2.6.15 起可用，覆盖 CentOS 7；
代价是极短命进程可能读不到命令行）。真实 Ubuntu 26.04 上反弹 shell、下载并执行、Webshell 三个新增自检全部检出
（各约 30 秒，即一个采集周期），连同 v0.2 的三个场景共 6 个，均纳入 CI；Agent 停止 / 重启状态识别正确，
资源上限生效。**未完成**：CPU 占用尚未在业务负载下实测；三种发行版 + CentOS 7 的兼容性需要在试运行中验证
（CI 只有 Ubuntu）；诱饵凭据需要文件访问审计，备份 / 杀毒软件会大量触发，需另行设计。

### v0.4 响应处置（✅ 已完成）

**目标**：从"能看到"到"能处理"，处置时间从小时级降到分钟级。

| 事项 | 规模 |
| --- | --- |
| 管理中心 → 节点的指令通道（节点轮询领取，沿用 mTLS 身份；指令有签名和有效期，防止重放） | M |
| 处置动作：主机上封禁 IP（iptables / nftables）、结束进程、隔离文件、**网络隔离主机**（只保留与管理中心的连接）、解除隔离 | M |
| 处置审批：高影响动作（隔离主机）需第二位管理员确认；所有动作进审计并可一键回滚 | S |
| 告警详情页一键处置；处置结果回传 | S |
| 联动：向防火墙 / 交换机下发封禁的 Webhook 适配接口（先做通用 Webhook，具体厂商按需求加） | S |

**验收**：从告警到隔离主机全程 < 2 分钟（含审批）；处置失败可见原因；回滚后业务恢复。

**结果**：四种动作及撤销在真实 Ubuntu 上全部验证（e2e 47 项）；隔离主机在独立网络命名空间中验证了两人审批、
隔离后其他地址不可达、与管理中心保持通信、解除后恢复。指令随上报下发，执行后立即回报结果，
从下发到完成的时间约为一个上报周期（默认 30 秒），满足 2 分钟目标（不含人工审批耗时）。
**未做**：向防火墙 / 交换机下发封禁的联动接口（按需求再加）；核心资产禁止隔离的白名单依赖 v0.5 的资产标签。

### v0.5 事件与攻击链（✅ 已完成，负责人推送待 v1.0 值守工作台）

**目标**：把零散告警串成"事件"，值守人员看到的是一次入侵的全过程，而不是几十条告警。

| 事项 | 规模 |
| --- | --- |
| 事件（Incident）：按主机、来源 IP、时间窗口自动聚合告警；事件状态（处理中 / 已解决 / 误报）、负责人、处置记录 | M |
| 攻击链时间线：同一事件内按 ATT&CK 阶段排列（扫描 → 利用 → 登录 → 持久化 → 横向） | M |
| 资产风险评分：漏洞、暴露面、近期告警、重要性标签综合打分，排序处理优先级 | S |
| 资产重要性与负责人：资产打标签（核心业务、域控、数据库），告警推送给对应负责人 | S |

**验收**：一次完整的模拟入侵（爆破 → 登录 → 持久化 → 横向）在控制台呈现为一个事件、一条时间线。

**结果**：爆破 → 登录 → 执行在测试中归为同一事件、三阶段自动升级为高危，时间线附带主机审计记录；
真实 Ubuntu 上蜜罐访问归入来源主机的事件。风险分附带逐项原因。**未做**：告警按资产负责人定向推送
（推送渠道目前按级别过滤，负责人路由放到 v1.0 值守工作台）；跨主机关联（同一攻击来源打多台主机）仍是多个事件。

### v0.6 Windows 与域控（Windows Agent ✅ 已完成；域控检测待测试域验证）

**目标**：覆盖企业内网的主体——Windows 终端、服务器和 AD 域。

| 事项 | 规模 |
| --- | --- |
| Windows Agent（Windows 服务）：采集安全日志（登录 4624/4625、进程创建 4688、服务安装 7045、计划任务 4698 等）、PowerShell 日志；可选读取 Sysmon | L |
| 一键安装：PowerShell 一行命令 + MSI 包，同样的公钥指纹校验 | M |
| 域控检测：Kerberoasting（4769 弱加密票据）、AS-REP Roasting、DCSync（4662 复制权限）、哈希传递 / 票据传递迹象、异常的域管登录、组策略变更 | L |
| Windows 侧处置：封禁 IP（Windows 防火墙）、结束进程、隔离主机 | M |
| 攻击模拟用例覆盖以上检测（在测试域环境中执行） | M |

**前提**：需要一套测试域环境（可用现有 Parallels 中的 Windows 11 加一台 Windows Server 搭建）。

**验收**：测试域中模拟的 Kerberoasting、DCSync、横向登录全部检出；Windows Agent 资源占用与 Linux 同等。

**结果**：Windows Agent 在 GitHub 的真实 Windows Server 上端到端验证 36 项：PowerShell 一行命令安装（公钥固定）、
开启审计、服务以 LocalSystem 运行；暴力破解、编码 PowerShell、清除日志、新建账户、加入管理员组、可疑服务全部检出；
自检（下载执行、Webshell）通过；封禁 IP、结束进程、隔离文件及撤销通过；停止感知、升级、卸载通过。
**未完成**：域控规则（Kerberoasting、AS-REP、DCSync、凭据传递）只有样例事件的单元测试，需要在测试 AD 域中用真实工具验证；
隔离主机在 Windows 上暂不支持；Windows Agent 资源占用尚未在业务负载下实测；RDP 开启网络级身份验证时
部分 4625 不带来源地址，这类爆破目前不计入统计。

### v0.7 威胁情报与外联分析（✅ 已完成）

| 事项 | 规模 |
| --- | --- |
| 威胁情报：导入 IP / 域名 / 文件哈希情报（开源情报源 + 自定义列表），命中即告警 | M |
| DNS 日志（Suricata / 内网 DNS 服务器）与可疑域名检测：新注册域名、DGA 特征、DNS 隧道 | M |
| 外联行为：周期性心跳（C2 Beacon 特征）、非工作时间大流量外传 | M |

**验收**：攻击模拟中的模拟 C2 心跳与情报命中流量全部检出。

**结果**：在真实 Ubuntu 上运行软件源中的 Suricata 8.0.3（输出 DNS v3 格式）抓取出口网卡流量，
真实的 DNS 查询、TLS SNI、连接地址三条情报路径全部检出（DNS / TLS 约 10 秒，流记录需等连接超时约 1 分钟）；
情报命中自检由 Agent 真实发出的 DNS 查询触发并通过；CI 机器正常出站流量没有产生 DGA / 隧道 / 心跳 / 外传误报。
C2 心跳在 e2e 中用构造的 Suricata 记录验证（真实场景需连续 15 分钟）。**未完成**：DGA、DNS 隧道、
非工作时间外传只有单元测试，需要在试运行的真实流量中观察误报率；文件哈希类情报尚未支持（需要 Agent 计算文件哈希）。

| 攻防演练模式：演练前暴露面收敛清单、演练期间告警加急推送、演练复盘报告 | S |
| 对外集成：Syslog / CEF 输出到 SIEM，开放 API 与 API Token | S |
| 国产化适配：麒麟 / 统信、鲲鹏 / 海光 / 飞腾验证；国密 TLS 评估 | M |
| 多组织 / 分支机构：按组织隔离资产与权限 | M |

**验收**：一名值守人员可管理 2000 台主机的日常告警；连续运行 30 天无人工干预的故障。

## 5. 贯穿各版本的工作

| 方向 | 内容 |
| --- | --- |
| 质量 | 每个版本：单元测试 + 真实 Linux CI + 攻击模拟自检全部通过才发布 |
| 自身安全 | 依赖漏洞扫描（`govulncheck`、`npm audit`）、SBOM、发布包签名与校验和；每个大版本做一次自我渗透测试 |
| 发布 | GitHub Release 提供安装包与校验和；升级说明写明数据库变更 |
| 文档 | 每条检测规则有说明和处置建议；部署、运维、故障排查文档随版本更新 |
| 反馈 | 误报标记、试运行记录、用户问题进入下一版本的优先级评估 |

## 6. 时间线概览

两条线并行：**开发线**按天推进，每个版本当天在 CI 中验证；**验证线**按日历时间推进，不随开发加速。

| 时间 | 开发线（AI 开发 + CI 验证） | 验证线（真实环境，需要人参与） |
| --- | --- | --- |
| 第 1 天 | v0.1.x CI、v0.2 蜜罐与攻击模拟 | 准备试运行机器，安装管理中心 |
| 第 2～3 天 | v0.3 主机检测深化 | 试运行开始：装 Agent / 探针，跑基线扫描 |
| 第 4 天 | v0.4 响应处置、v0.5 事件与攻击链 | 试运行观察：记录告警与误报 |
| 第 5～7 天 | v0.6 Windows（先做 Agent 与本机检测） | 搭测试 AD 域（Windows Server + 一台域内机器） |
| 第 2 周 | v0.6 域控检测、v0.7、v0.8 | 试运行第一轮反馈 → 修复；在测试域验证域控检测 |
| 第 3 周 | v1.0；按反馈修复与调优 | 用攻击模拟 + 一次内部红蓝对抗做验收 |

开发约 2 周可以全部完成；**能否算"做成"取决于验证线**：试运行至少 1～2 周、一次真实的红蓝对抗。
建议每完成一个版本就部署到试运行环境，而不是等全部开发完再一起上线——问题越早暴露，修起来越便宜。

如果近期有攻防演练：先做 **v0.2 蜜罐 → v0.3 命令审计与反弹 shell → v0.4 封禁 IP 与隔离主机**，
开发 3～4 天即可形成"诱捕 + 主机检测 + 快速处置"的最小防守闭环，剩余时间全部用于在演练环境中试运行和调优。

## 7. 风险

| 风险 | 应对 |
| --- | --- |
| 试运行暴露的问题多于预期，挤占新功能 | v0.1.x 不设功能目标，修完再进入 v0.2 |
| eBPF 在老内核不可用 | auditd 回退方案；最低支持 CentOS 7（内核 3.10） |
| Windows 开发与测试环境成本 | 单独立项；先用 Sysmon + 事件日志，不做驱动 |
| 新检测带来误报，值守疲劳 | 新规则先"观察"模式；误报率超过 20% 的规则不推送 |
| 处置动作误伤业务 | 审批、白名单（核心资产禁止自动隔离）、一键回滚 |
| 开发快于验证，未经真实环境检验的功能堆积 | 每个版本部署到试运行环境后再开始下一个大版本；CI 验证不通过不合入 |
| 速度带来的质量风险（如本次开发中发现的死锁、脚本兼容问题） | 每个版本都有攻击模拟和 CI 回归；发布前在试运行环境观察至少 1 天 |
